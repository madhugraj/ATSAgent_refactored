## 2. Request pipeline wiring and whether "separate API" is feasible

`vite.config.ts`: `tanstackStart({ server: { entry: "server" } })` redirects Start's server entry to **src/server.ts**; `nitro({ preset: "node-server" })` produces `.output/server/index.mjs`. src/server.ts wraps `@tanstack/react-start/server-entry` and handles, for every request (SSR pages, `/_serverFn/<id>`, `/api/*`, `/metrics`):

1. `import "./lib/error-capture"` side-effect (global error hooks, `consumeLastCapturedError`) + h3 swallowed-500 normalisation, client-abort -> 499, HTML error page.
2. `withRequestContext(contextFromHeaders)` — AsyncLocalStorage trace; `traceparent`/`x-request-id` response headers; log.ts reads it.
3. CSRF guard: Sec-Fetch-Site / Origin allow-list (PUBLIC_SITE_URL + localhost:3000/8080/8081/9000) for mutating `/api/auth/*` and `/_serverFn/*` (cookie is SameSite=None).
4. Rate limiting via `allowRequest(ip:path)`: 60/min for `/api/public/*`, `/_serverFn/*`, `/metrics`; `AUTH_RATE_LIMIT` for non-GET `/api/auth/*` except session/me. Server-fn path already names the function -> per-function bucket.
5. `/metrics` (METRICS_TOKEN bearer, timing-safe; 404 when unset).
6. Metrics `recordRequest`, `requestStarted`, structured `http.request` log, SLI flusher start (`slo.server.startSliFlusher`) lazily.
7. Security headers: HSTS everywhere; CSP with per-response nonce stamped into SSR HTML, X-Frame-Options.
   src/start.ts adds Start request middleware: errorMiddleware + `createCsrfMiddleware` (filter serverFn) — a second CSRF layer.
   Auth is NOT in server.ts: it is per-server-fn middleware (`requireOrg` etc.) and per-route code in /api/auth and /api/public.

**Can server fns be served from a separate app?** Practically no, not with this version. Server functions are compiled by the Start vite plugin: client bundle gets RPC stubs that POST to `/_serverFn/<hashed id>` on the same origin, and the server handler registry is generated in the same build (ids derived from file path + export). Splitting UI and handlers into two builds would break id matching, SSR-time direct calls, `getRequest()`, importProtection mocks, and the same-origin CSRF/cookie model (CSP `connect-src 'self'`, SameSite cookie, csrfGuard allowed origins). There is no supported "remote server-fn host" in 1.169.

**Recommendation:** keep ONE TanStack Start deployable (call it `apps/web` or `apps/app`) that owns: routes (UI + `src/routes/api/**` file routes), `*.functions.ts` thin wrappers (validator + auth middleware + call into package core), server.ts entry, start.ts. Move all business logic into `packages/*` (`@pkg/db`, `@pkg/auth`, `@pkg/ai`, `@pkg/observability`, domain packages). `apps/api` becomes meaningful only for non-Start processes: voice worker, parser worker, and optionally a scheduler/cron runner (agent-tick etc. could become a worker instead of HTTP). If a true REST API is wanted later, build it as a separate Hono/h3 app calling the same packages and re-implementing the server.ts pipeline (rate limit, CSRF/CORS, metrics, trace, error capture) via a shared `@pkg/platform-http` — so extract that pipeline from server.ts into composable functions now.

Must stay in the HTTP entry of whatever serves requests: error-capture import (first), request context, csrfGuard, rate-limit routing rules, metrics + /metrics, SLI flusher start, security headers/CSP nonce stamping, h3 500 normalisation.

In-scope: rate-limit, step-up, parser-sandbox, guardrails(+p1), hidden-text, redteam-check, observability(+clarity), training-data, agent-gateway, integration.verify, run-limits.
Path concerns:

- They import src via RELATIVE paths, mostly dynamic: `import("../drizzle/schema")` 88x, `import("../src/server/db")` 49x, ai-gateway 39x, agents/runtime 25x... Not via `@/` alias (only 1 alias use).
- 20+ `mock.module("../src/server/db", ...)`, `mock.module("../src/lib/ai-gateway.server", ...)` etc. Bun mocks match by resolved specifier/path: after moving files, a stale mock path silently fails to intercept and the test may hit a real DB/provider or pass vacuously. Must rewrite mocks to package specifiers and verify each mock actually applies.
- But src code itself uses `@db/schema` and `@/` — bun resolves via tsconfig paths from repo root; tests in a package need their own tsconfig paths or workspace package names.
- Tests read repo files: agent-governance reads scripts/agents.lock.json; voice-charter reads docs/voice-agents-charter.md via import.meta.url — relocating tests breaks these relative URLs.

## 8. Risks / gaps a migration team would miss

1. Server-fn ids and importProtection: vite `importProtection.client.files: ["**/server/**"]` mocks anything under a `server/` path in the client bundle. Moving server code into `packages/foo/src/index.ts` (no `server` segment) disables that protection — node-only code (db, secrets) could leak into the client bundle or fail the build. Recreate with `server-only` specifier or package-level globs.
2. auth.middleware must stay unmocked/introspectable by the server-fn compiler (vite comment) — don't put it under a `server/` folder in the new layout.
3. AsyncLocalStorage singletons (request-context, agents/context aiSubjectScope/agentRunScope): if a package is duplicated in the bundle (two copies via different resolution paths) context silently disappears -> AI usage not attributed to runs, training capture loses subject (erasure cascade invariant), logs lose trace. Enforce single instance (workspace dedupe, `resolve.dedupe`).
4. Rate limiter keys on URL path; a separate API host or path prefix change (`/api/v1`, different `/_serverFn` base) would silently drop limiter coverage (AGENTS.md invariant). CSRF allow-list hardcodes origins/ports (localhost:9000 combined dev).
5. Two CSRF layers (server.ts csrfGuard + start.ts createCsrfMiddleware); start.ts comment: defining start.ts disables Start's default CSRF, so it must be re-added — easy to lose when moving start.ts.
6. `/api/auth/confirm` (GET) and `/api/auth/me|session` are not rate-limited; feeds GET is limited only because it's under /api/public.
7. Voice worker bundle externalises `#tanstack-*` — it already depends on modules that reach server-fn virtual modules; separating it into apps/voice-worker will surface hidden imports of `@tanstack/react-start`.
8. Build ordering: `vite build` empties `.output`, workers build after; Dockerfile copies only .output. Per-app outputs must still land in the single image (or create per-worker images and update deploy.yml + scripts/deploy.sh + GKE manifests).
9. slo.server is started lazily from server.ts and its evaluator runs on agent-tick — the SLO pipeline spans observability + agents + email; burn alerts silently stop if agent-tick moves.
10. Schema typing via `$type<import("../src/lib/...")>` — moving src/lib breaks types without runtime errors (jsonb types become any-ish compile errors only).
11. AGENTS.md: agents.lock.json and `bun run agents:lock` hash agent definitions — moving definitions.ts/tool files may change hashed paths and fail CI.
12. ai_interviewer/ (Python SIP prototype) is entirely gitignored and contains google-credentials.json locally — not part of the repo; exclude from monorepo, never commit. extension/ (MV3 Chrome extension, plain JS, host_permissions to site, talks to /api/public/capture & distribution with credentials) has no build; can become apps/extension unchanged, but CAPTURE_EXTENSION_IDS CORS must follow.
13. Docs invariant: README, DEPLOYMENT-GCP.md, infra/DEPLOYMENT-HANDOFF.md, SECURITY.md, roadmap.md must be updated in the same change; er-diagram generation script (scripts/gen-er-diagram.mjs) reads drizzle/schema.ts path; migrate-pg.mjs reads drizzle/pg-migrations path.
14. env reads scattered outside env.ts; .env.production.example incomplete for workers.
15. Postgres-backed rate limiter table and SLI flusher share the web's DB pool — a separate API app doubles pools/connections.
