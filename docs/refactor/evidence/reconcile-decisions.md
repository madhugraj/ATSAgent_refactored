# §4 schema reconciliation — production-only objects (2026-11-25)

**Status:** decisions recorded for product-owner/reviewer approval. Nothing executed against production —
every `reconcile-*.sql` action here runs only inside the release plan's gates (§4 recorded → §6 rehearsal
green → product-owner release approval), and only the migration-window-safe items are scheduled.

**Method:** production's `pg_migrations` re-read read-only (30 applied; the 7 production-only files
confirmed; last common point `0022`). A fresh reference DB was migrated to exactly the common point and its
schema dumped; a full schema-only dump of production was diffed against it (tables, sequences, indexes,
columns). Each production-only object was then mapped by a dedicated research pass (production DDL +
read-only row counts + all 96 repo migrations + `drizzle/schema.ts` + `src/` references + `git log -S`),
and every decision was independently adversarially verified against the repo (19/19 agree, no corrections).

## Execution notes

- All drops are idempotent (`drop … if exists`) and collected in one `reconcile-*.sql` per release, run by
  hand (the migrate runner picks up only named pending files — reconcile files are executed explicitly, not
  by the runner).
- Guard re-checks immediately before any drop (read-only): `candidates.gender` non-null = 0;
  `inbox_messages.owner_id` non-null = 0; `ai_trace_steps` rows = 0. Rollback target if anything
  reappears: the pre-migrate snapshot.
- The two keep-but-quiet tables (`app_logs`, `ai_traces`) and the `platform_settings` credential export are
  **post-image-swap** actions on the release-day runbook, not migration-time steps.
